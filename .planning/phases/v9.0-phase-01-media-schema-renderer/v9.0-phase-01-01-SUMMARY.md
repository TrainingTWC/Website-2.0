# v9.0 Phase 01 — Plan 01 SUMMARY

## What shipped

Backend foundation for Brewing Studio Media:

1. **`src/lib/studioSlots.ts`** — Canonical slot registry. Exports `STUDIO_SLOTS`, `StudioSlot`, `isValidSlotKey`, `MEDIA_KIND_SIZE_LIMITS`, `MediaKind`. Five slots: `brew_method`, `brew_step`, `signature`, `product`, `ambience`. Five kinds with per-kind size limits (image 5MB, video 25MB, gif 10MB, lottie 200KB, glb 15MB).

2. **`convex/schema.ts`** — Added `media` table with 12 fields and 3 indexes (`by_slot_key`, `by_status_slot`, `by_creation`).

3. **`convex/media.ts`** — Six exports as specified: `generateUploadUrl`, `saveMediaRef`, `getActive`, `listBySlot`, `setActive`, `deleteMedia`. All write/admin mutations gate on `requireAdmin(ctx)` as first awaited statement. `getActive` is intentionally public (customer-facing query) and only returns `status === "published"` rows.

4. **npm deps installed**: `lottie-react@^2.4.1`, `blurhash@^2.0.5`, `react-blurhash@^0.3.0` (4 packages total with transitive).

## Deviations / decisions

- **Cross-tree import path**: PLAN allowed for either `import { MEDIA_KIND_SIZE_LIMITS } from "../src/lib/studioSlots"` OR inlining as a fallback. Inspecting `convex/tsconfig.json` showed `"include": ["./**/*"]` (scoped to convex/), so the cross-tree path would not have resolved under the Convex bundler. **Chose to inline** `MEDIA_KIND_SIZE_LIMITS` at the top of `convex/media.ts` with a comment pointing to the source-of-truth in `src/lib/studioSlots.ts`. Adding new kinds requires updating both files — this is documented inline.

- **`aiMeta` arg typing**: PLAN used `v.any()` for the arg validator. Tightened to a `v.object({ provider, model, prompt, seed?, costUsd?, predictionId? })` so the validator matches the schema column exactly. No functional change.

- **Did not run `npx convex dev`** to regenerate `_generated/api.d.ts` — Convex dev requires interactive auth and would block the autonomous run. `npx tsc -p convex/tsconfig.json` succeeded against the existing generated types. The schema additions are additive (new table, no changed columns), so the generated bindings remain valid until next deploy. Plan 02 will need fresh bindings; document there.
