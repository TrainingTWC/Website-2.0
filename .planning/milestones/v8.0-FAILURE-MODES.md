# Failure Modes: v8.0 — Add-to-Cart → Delivered

**Companion to:** `v8.0-REQUIREMENTS.md`
**Purpose:** Exhaustive catalog of every place the order flow can break, the customer-visible symptom, the root cause, and the mitigation owned by a specific requirement ID.

Read this end-to-end before designing any phase. Every failure mode here MUST have either (a) a requirement that prevents it, (b) a requirement that detects + recovers from it, or (c) an explicit "accepted risk" decision.

Legend: **REQ** = requirement ID that addresses it · **OPS** = operational fallback · **DET** = how we detect it

---

## STAGE 1: Product Discovery → Add to Cart

### 1.1 Product is added but the price changed since the page loaded
- **Symptom:** Customer sees old price in cart, server rejects checkout with "total mismatch".
- **Root cause:** Product price edited in admin between page-render and cart action.
- **REQ:** CRT-03 (`cartValidate` on drawer open + before checkout, returns `priceChanged`).
- **UI behavior:** Show a non-dismissable inline banner with old vs new price, "Update cart" CTA. Block checkout until acknowledged.
- **DET:** `cartValidate` query result diff.

### 1.2 Product is added but goes out of stock before checkout
- **Symptom:** "Place order" button errors generically.
- **Root cause:** No real-time stock check on the cart screen; race with another buyer.
- **REQ:** CRT-03 + CHK-02 (`inventoryHolds`; reservation only at `createDraftOrder`).
- **UI behavior:** Soft warning at cart drawer open if stock < 5; hard block at checkout with "remove or wait" prompt.

### 1.3 Product is deleted while still in the cart
- **Symptom:** Cart shows a phantom item; checkout silently strips it or fails.
- **REQ:** CRT-03 (`removed: true` flag).
- **UI behavior:** Visibly cross out, "We've removed this — it's no longer available."

### 1.4 Cart in localStorage exceeds 5MB (Safari iOS limit)
- **Symptom:** localStorage write throws QuotaExceededError; cart resets silently on next load.
- **DET:** Catch the throw, log to `clientErrors`.
- **OPS:** Cap cart at 50 line items, refuse to add and toast.
- **Accepted risk:** Below cap, no realistic way to hit 5MB.

### 1.5 Cart is on Device A; customer switches to Device B
- **Symptom:** Cart "disappears" on the other device.
- **REQ:** CRT-01 (`cartSnapshots` server-side when customer is known). For anonymous sessions, cart stays local — this is an accepted limitation.

### 1.6 Discount code is claimed but the code is then deactivated in admin
- **Symptom:** Customer sees a discount pill that vanishes at checkout.
- **REQ:** Existing v4.0 server re-validation (D-03) — silent drop, retry path. v8.0 makes this explicit in UI: line item "Discount no longer valid".

### 1.7 Multiple cart tabs open; updates clobber each other
- **Symptom:** Tab A adds item, Tab B (older snapshot) writes back and removes it.
- **OPS:** `storage` event listener re-reads localStorage on focus. Last-write-wins is acceptable for a guest cart.
- **Accepted risk:** Documented; no real-time CRDT.

## STAGE 2: Checkout Form

### 2.1 Pincode is non-serviceable
- **Symptom:** Order is accepted then ops manually cancels later.
- **REQ:** ADR-03 (`pincodeServiceability` lookup blocks checkout).
- **UI behavior:** As soon as pincode is typed (6 digits), validate. If non-serviceable: show "We don't deliver to {pincode} yet — leave your email to be notified."

### 2.2 Pincode is serviceable for prepaid only but customer picks COD
- **REQ:** ADR-03 (`codAvailable: false` disables the COD radio).
- **UI:** Greyed-out COD option with tooltip "Cash on Delivery isn't available for {pincode}."

### 2.3 Phone number is fake / non-WhatsApp
- **DET:** Notification delivery webhook (`notificationOutbox.lastError = "INVALID_NUMBER"`).
- **OPS:** Auto-fallback channel chain (WhatsApp → SMS → Email). If all three fail, ops gets a `notification_undeliverable` alert on the Action Required queue.

### 2.4 Email is mistyped (gmial.com, yaho.com)
- **OPS:** Soft validator suggests "Did you mean gmail.com?" at blur. Not blocking — they may intentionally use a one-time inbox.

### 2.5 Address fields contain emojis / Unicode that break the courier API
- **OPS:** Sanitization layer in `createDraftOrder` strips non-printable and emoji ranges. Stored sanitized; original retained as `customer.addressRaw` for debugging.

### 2.6 Customer abandons mid-checkout
- **REQ:** ABN-01–03 (abandoned cart recovery). Trigger requires phone or email already captured — if checkout abandonment happens before contact fields are filled, we don't have the customer to message.
- **OPS:** Capture phone/email at the FIRST touched field (with autosave to `cartSnapshots`) — don't wait for "Place Order".

### 2.7 Customer is using an autofill that puts state code in the city field
- **DET:** State validator rejects (PIN-to-state cross-check, ADR-04).
- **UI:** Inline correction "Pincode {x} is in {state}, not {city}". One-click fix.

### 2.8 GPS autofill (v3.0-phase-02) returns the wrong building
- **Accepted risk:** GPS is best-effort; final field is editable. Customer is responsible for accuracy.
- **OPS:** Last-mile delivery failures with "address not found" become a `delivery-failed` order event with the original GPS coords logged → enables a heatmap of bad addresses.

## STAGE 3: Order Creation (`createDraftOrder`)

### 3.1 Server-computed subtotal disagrees with client subtotal
- **REQ:** Existing API-01 (already shipped).
- **Hardened in v8.0:** Error response includes the per-line diff, not just a generic message. UI shows exactly which item's price moved.

### 3.2 Inventory reservation succeeds but draft insert fails
- **Symptom:** Held inventory with no draft.
- **DET:** Convex mutation atomicity — entire mutation runs in one transaction, so this can't happen for in-process work. Cross-process failures (e.g., a Convex deploy mid-mutation) trigger a rollback.
- **OPS:** Hold-expiry cron (15 min) reclaims any orphaned holds regardless of cause.

### 3.3 Two customers try to buy the last unit simultaneously
- **REQ:** CHK-02 — Convex mutations are serialized per-table-row; the second `createDraftOrder` reads the updated hold sum and rejects with `OUT_OF_STOCK`.
- **UI behavior:** Second customer sees a recovery screen: "Sold out — notify me when back in stock" (writes to `productWaitlist`).

### 3.4 Discount code reaches `maxUses` between claim and finalize
- **REQ:** Existing v4.0 atomic increment in `claimDiscount`.
- **Hardened:** `submitOrder` re-validates and silently drops the discount if it just expired. UI shows post-checkout "Discount no longer applied — completed at full price" with a toast.

### 3.5 Customer record merge conflict (two existing customers share a phone)
- **DET:** CRM-02 lookup returns >1 row.
- **OPS:** Both rows are flagged `mergeConflict: true`; new orders are linked to the most-recently-active record; ops dashboard shows a "Resolve duplicates" queue.

### 3.6 Customer marked itself as deleted (GDPR request) but reorders
- **Accepted policy:** A deleted customer (`customers.deleted: true`) creates a fresh record on reorder. The old record is retained only for tax/compliance purposes, scrubbed of name/contact (phone hashed).

## STAGE 4: Payment

### 4.1 Razorpay modal is opened but customer closes without paying
- **REQ:** PAY-05 reconciliation cron auto-cancels after 30 min and releases inventory.
- **UI behavior:** "Resume payment" deeplink valid for 15 min (uses the same draft).

### 4.2 Payment succeeds on Razorpay but webhook never arrives
- **REQ:** PAY-05 reconciliation cron picks it up within 15 min, finalizes the order.
- **Failure case:** Razorpay outage → manual reconciliation via admin tool `reconcilePayment(orderId)` that re-queries Razorpay directly.

### 4.3 Webhook arrives but signature verification fails
- **REQ:** PAY-02 — logged to `webhookFailures` with full headers + body, returns 400. Razorpay retries with backoff.
- **DET:** Alert if `webhookFailures` grows > 10/hour (indicates a key rotation or attack).

### 4.4 Webhook is replayed (Razorpay retry storm)
- **REQ:** PAY-03 — idempotency via `processedWebhookEvents`.

### 4.5 Frontend success callback fires but webhook says failed
- **Trust hierarchy:** Webhook wins. Frontend success is advisory. Customer briefly sees "Order confirmed" then a corrective notification if webhook contradicts.
- **OPS:** Rare; usually means a 3D-Secure challenge that the frontend SDK misreported. Ops follows up manually.

### 4.6 COD order's `requestedPaymentAmount` differs from cash collected by courier
- **DET:** Courier remittance reconciliation (manual or via Shiprocket API).
- **OPS:** Discrepancy flagged on `Action Required` queue; ops adjudicates.

### 4.7 Customer enters a different phone at delivery than at checkout
- **DET:** Courier captures actual recipient; courier webhook update.
- **OPS:** New phone added to customer record as a secondary contact, NOT replacing the primary.

### 4.8 Razorpay double-charges (one capture, two debits)
- **Rare; provider-side bug.** Customer files a ticket; manual refund via Razorpay dashboard + insert refund row.

### 4.9 Refund webhook arrives before refund row exists
- **OPS:** Webhook handler creates the refund row if missing (`upsert by razorpayRefundId`).

### 4.10 GST input fields needed for B2B
- **Accepted scope:** Out of scope for v8.0 (B2C-only); add `gstin` field to `customers` in v8.1 if demand emerges.

## STAGE 5: Fulfillment

### 5.1 Admin transitions `confirmed → delivered` skipping `packed/shipped`
- **REQ:** FUL-01 enforces state machine; this throws `INVALID_TRANSITION`.
- **OPS:** Force-transition exists for data backfill — gated by `superadmin` role only and writes a special `system:force` actor to `orderEvents`.

### 5.2 Tracking ID typo
- **OPS:** Courier webhook fails to associate. Order sits in `shipped` indefinitely.
- **DET:** Cron flags orders in `shipped` > 7 days as `delivery_stale`.
- **OPS UI:** "Update tracking" action on stale rows.

### 5.3 Multiple orders, same customer, shipped together as one parcel
- **OPS:** `parentOrderId` is added to `orders` schema (optional) to group bundled shipments. Tracking ID can be shared. UI groups them in the customer timeline.

### 5.4 Customer requests address change after `confirmed` but before `packed`
- **OPS:** Allowed via `editShippingAddress` mutation — only allowed in `confirmed` or earlier. Logs an `address_changed` event. After `packed`, requires cancellation + re-order.

### 5.5 Courier marks delivered but customer claims not received
- **Process:** Open dispute (`disputes` table), ops investigates via courier proof-of-delivery. If unresolved: refund as goodwill, mark `lost-in-transit` with `disputeOutcome: "goodwill_refund"`.

### 5.6 Delivery attempted but recipient unavailable (NDR — non-delivery report)
- **Courier webhook:** Status `ndr_attempt_1`, `ndr_attempt_2`, `ndr_failed`. We allow up to 3 attempts before transitioning to `delivery-failed`.
- **Notification:** Customer is messaged on each NDR with a reschedule link.

### 5.7 RTO (Return to Origin) due to repeated NDR
- **State:** `delivery-failed → returned` (without customer return request). Inventory restocked per RTN-04.

### 5.8 Wrong item shipped
- **DET:** Customer complaint.
- **OPS:** Issue replacement (new order linked via `replacementForOrderId`) + return label for the wrong item. No charge.

### 5.9 Courier loses the parcel
- **Process:** Courier-acknowledged loss → `lost-in-transit` → automatic full refund. Loss claim filed with courier in background.

### 5.10 Damaged on delivery
- **OPS:** Customer uploads photo via the public order tracking page. Ops decides refund vs replacement.

## STAGE 6: Post-Delivery / Returns / Refunds

### 6.1 Customer requests return after the 7-day window
- **REQ:** RTN-05 — API-level reject. UI shows "Return window expired on {date}" with a "Contact us" escape hatch.

### 6.2 Customer asks for partial refund (e.g., 1 of 3 items)
- **Schema:** `refunds.lineItems: optional array` — supports partial. UI requires per-line selection and reason.

### 6.3 Returned product is damaged and not resellable
- **REQ:** RTN-04 — admin marks `resellable: false`; write-off recorded.

### 6.4 Refund call to Razorpay fails (insufficient balance, expired card)
- **REQ:** RTN-03 — daily cron retries up to 5 times. After 5 failures, ops alerted; manual refund (UPI transfer) and `manualRefundProof` stored.

### 6.5 Customer changes consent (revokes marketing) after delivery
- **REQ:** CRM-01 consent flags. Notification system reads consent at send-time, not enqueue-time.

### 6.6 GDPR/DPDP deletion request
- **Process:** `requestDeletion` mutation marks customer `deleted: true`, scrubs name/email/phone (hash retained for fraud-check), keeps `orders` (legal retention 7 yrs). All `customerEvents` for that customer are deleted immediately.

### 6.7 Customer never opens the feedback request
- **Accepted.** Feedback is optional. One reminder at 72 hrs, then silent.

## STAGE 7: Cross-cutting / Systemic

### 7.1 Convex deployment rolls back schema
- **Risk:** Field types change incompatibly between deploys.
- **Mitigation:** All new schema fields in v8.0 are `v.optional()`. No required field is added to an existing table without a backfill migration committed in the same phase.

### 7.2 `MISTRAL_API_KEY` / `RAZORPAY_*` env vars missing in prod
- **DET:** Startup self-check action `selfTest` returns degraded status; admin dashboard shows a red banner.

### 7.3 Cron job overlaps with itself (long-running reconciliation)
- **Mitigation:** Each cron acquires a `cronLocks` row before running, releases on finish or expiry. Skipped runs are logged.

### 7.4 Notification spam (template bug sends 10x)
- **Mitigation:** `notificationOutbox` has a unique constraint on `(customerId, templateKey, orderId, dayBucket)`. Re-enqueueing the same notification on the same day is a no-op.

### 7.5 Customer impersonation (someone enters another person's phone at checkout)
- **Accepted risk** in a guest-checkout system. Mitigations: order tracking page requires both `orderId` AND last-4 of phone; sensitive fields (full address, full phone) shown to admin only.

### 7.6 Bot / scripted ordering (sneaker-bot pattern on flash sales)
- **DET:** Rate-limit `createDraftOrder` per IP (max 3/min) and per phone (max 5/hour).
- **OPS:** Repeat offenders → IP block via Convex HTTP action allowlist.

### 7.7 Webhook endpoint DoS
- **Mitigation:** Razorpay/courier endpoints validate signature BEFORE doing any database work. Unsigned requests return 401 in < 10ms.

### 7.8 PII leakage via order URL
- **REQ:** Existing PII-stripping in `getOrder` (already shipped). v8.0 extends: the public order page never reveals full phone or address — only `XXXX1234` and "City, State".

### 7.9 Time zone bugs (UTC vs IST)
- **Mitigation:** All timestamps are epoch ms (UTC). Display layer formats to IST. Crons use a single `dayBucket()` helper to avoid drift.

### 7.10 Customer-facing string is wrong / typo
- **REQ:** NOT-03 — templates in `siteContent`, editable without deploy.

### 7.11 Backfill migration runs twice
- **Mitigation:** Every migration uses an idempotency marker (`migrationsRun` table). Skipped if already run.

### 7.12 Customer-events table grows unbounded
- **REQ:** EVT-02 — 90-day retention for low-value events, indefinite for high-value.

### 7.13 Razorpay key rotation
- **Process:** Both old and new keys are valid during the rotation window. `RAZORPAY_KEY_ID_NEXT` env var accepted as a fallback by signature verification.

### 7.14 Dependency on third-party (Razorpay / Delhivery / Shiprocket) is down
- **Mitigation:** `selfTest` action pings each on a 5-min cadence. Status surface on admin dashboard. During outage, COD-only fallback can be toggled by `siteContent.crm.featureFlags.prepaidEnabled = false`.

### 7.15 Race condition: customer pays AND requests cancellation in the same minute
- **Resolution:** Payment webhook wins (it's the immutable event); cancellation request is rejected with "Order already confirmed — request refund instead."

## Severity & Priority Matrix

| Severity | Definition | Examples |
|----------|------------|----------|
| **P0 — Blocks revenue** | Payment fails or order can't be placed | 4.1, 4.2, 4.3, 3.1, 7.2 |
| **P1 — Silent data corruption** | Wrong record state, can't recover automatically | 3.2, 3.5, 4.5, 4.8 |
| **P2 — Customer-visible defect** | User sees something wrong but order still works | 1.1, 1.3, 2.1, 5.1 |
| **P3 — Operational drag** | Ops has to manually intervene | 2.3, 5.2, 5.5, 6.3 |
| **Accepted** | Documented limitation, no fix planned | 1.4, 1.7, 5.5 (when goodwill route is fine) |

Each P0/P1 failure mode MUST have a regression test in the phase that addresses it.
