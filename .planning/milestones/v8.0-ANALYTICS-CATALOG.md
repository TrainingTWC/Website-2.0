# v8.0 — Analytics & Friction Catalog

> Companion to `v8.0-DATA-CAPTURE.md`. That doc defines the **event schema** (what tables/fields exist). This doc defines the **100+ behavioural data points** we capture and the **derived friction metrics** we report on — focused on dropouts, abandonment, hesitation, and point-of-failure analysis from first product view through delivered/refunded.

Every data point below is tagged:
- **Source** — `client` (browser instrumentation) | `server` (Convex mutation/query) | `derived` (computed from raw events)
- **Storage** — Convex table the raw event lands in (`customerEvents`, `customerEventsAnonymous`, `orderEvents`, `paymentLog`, `clientErrors`, `cartSnapshots`, `pageViews`, `webVitals`, `notificationOutbox`)
- **Purpose** — what business question it answers

Funnel stages mirror `v8.0-FAILURE-MODES.md`:
1. Discovery & Browsing
2. Product Detail & Intent
3. Cart Build
4. Cart Abandonment Window
5. Checkout — Identity
6. Checkout — Address
7. Checkout — Review & Discount

## 14. Derived Friction Metrics (dashboards)

| Metric | Formula | Stage |
|---|---|---|
| **Add-to-cart rate** | sessions with ≥1 ATC / sessions with ≥1 PDP view | 2→3 |
| **Cart-to-checkout rate** | sessions with checkout_initiated / sessions with ATC | 3→5 |
| **Cart abandonment rate** | abandoned carts / (abandoned + completed) | 4 |
| **Time-to-abandon (median)** | median(last_activity − cart_first_add) for abandoned carts | 4 |
| **Step-completion rate per checkout step** | sessions advancing to next step / sessions reaching step | 5–8 |
| **Step-abandon heatmap** | dropout count by `last_interaction` element | all checkout |
| **Payment-attempt success rate** | captured / attempted, per method | 9 |
| **Payment-failure reason mix** | grouped count by `failureReason` | 9 |
| **Razorpay modal dismiss rate** | dismissed / opened | 9 |
| **Webhook reconciliation lag (p95)** | p95(webhook_received_at − razorpay_event_at) | 9 |
| **Pincode-fail abandonment rate** | abandons within 5 min of pincode_fail / pincode_fail events | 6 |
| **Discount-fail abandonment rate** | abandons within 5 min of discount_rejected / discount_rejected events | 7 |
| **Recovery email conversion** | recovered orders / recovery messages sent | 4 |
| **Order-stuck-in-state count** | active orders with state age > SLA, per state | 11 |
| **Return rate** | returns / delivered orders | 12 |
| **Return reason mix** | grouped count by `returnReason` | 12 |
| **Repeat-purchase rate (30d)** | customers with ≥2 orders in 30 days / customers with ≥1 order | 12 |

## 15. Point-of-Dropout Attribution Model

Every abandoned session ends with a **dropout fingerprint** computed by a cron and stored on `customerEventsAnonymous` (or `customerEvents` once identified):

```
{
  lastStage: 5,                        // 1–12 funnel stage
  lastInteraction: "checkout.phone",   // dotted UI element id
  lastErrorCode: "phone.invalid",      // optional
  lastNetworkState: "online",
  timeOnLastStageMs: 47230,
  cartValue: 1280,
  cartItems: 2,
  recoveryEligible: true,              // identity captured?
  recoveryChannel: "email"             // best contact available
}
```

This gives us a **single grouping key** for cohort analysis ("show me all dropouts where lastInteraction = `checkout.pincode` and reason = unserviceable in last 7 days") without scanning raw event streams every time.

## 16. Implementation Notes (for phase planning)

- Client instrumentation goes through a thin `track(eventName, props)` helper that **batches** and **debounces** (no event per keystroke; debounce per-field). Lives in `src/lib/analytics.ts`.
- All client events carry `anonId`, `sessionId`, `route`, `ts`, `viewport`, `connection`, `experimentBuckets` automatically.
- Server events (state transitions, webhook receipts) emit via the existing pattern in `convex/orders.ts` (the `orderEvents` writer added in Phase 1).
- Sampling: keep 100% of order/payment events; sample 10% of `impression` / `pdp_dwell` / `scroll_depth` to control volume.
- PII rule: phone/email **never** stored in `customerEventsAnonymous`. Identity-resolution happens server-side via `customers` table joins.
- Retention: raw `customerEventsAnonymous` rolls up to daily summaries at 30 days; full events retained 90 days; identified `customerEvents` retained per `v8.0-DATA-CAPTURE.md` retention table.
