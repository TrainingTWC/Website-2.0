## Phase 1 — CRM Data Foundation

**Goal:** A customer is a first-class entity. Every existing order is linked to a real customer record. The schema, indexes, and timeline infrastructure exist so the next two phases have something to write to.

**Requirements covered:** CRM-01–04, ADR-01–04, EVT-01–03, SEG-01–03

### Tasks

1. **Schema additions** (single deploy):
   - `customers`, `customerAddresses`, `pincodeServiceability` (seeded from CSV — see scripts task below)
   - `customerEvents`, `customerEventsAnonymous`
   - `customerSegments`, `customerNotes`
   - Add `customerId: v.optional(v.id("customers"))` to `orders`
2. **Backfill migration** (`convex/migrations.ts`):
   - `backfillCustomers` — iterates `orders`, upserts a `customers` row per unique `(phone, email)`, links order back via `customerId`
   - Idempotent — uses `migrationsRun` marker
3. **Identity merging logic** in `customers.ts`:
   - `findOrCreateByContact({ phone, email })` — soft-merge logic per CRM-02
   - `mergeCustomers({ winningId, losingId, reason })` — admin-only; reassigns all FKs (orders, addresses, events)
4. **Events emitter**:
   - `src/lib/analytics.ts` — single client emitter `track(eventType, properties)`; batches up to 10 events or 5 seconds, then POSTs to a Convex mutation
   - Mutation: `customerEvents.batchInsert` (size-capped at 50, schema-validated)
   - Anonymous → identified merge: `linkAnonymousSession(sessionId, customerId)` (EVT-03)
5. **Pincode serviceability**:
   - Seed `pincodeServiceability` table from `scripts/seedPincodes.ts` (uses Delhivery's public serviceability CSV if available, else India Post bulk data)
   - Query helper `checkServiceability(pincode)` returns `{ serviceable, codAvailable, etaDays, partner }`
6. **Segment computation**:
   - Internal mutation `recomputeSegmentsForCustomer(customerId)` triggered by `submitOrder` and `transitionOrder`
   - Daily cron `recomputeRfmQuintiles()` updates the population baselines used by segment thresholds
7. **Admin Customers tab**:
   - Reuses existing `admins.permissions.customers` flag
   - List view: search by phone/email/name, filter chips by segment, sortable columns
   - Drawer view: orders list, event timeline, addresses, consent flags, notes

### Success Criteria

- All existing orders have a non-null `customerId` after backfill
- Two checkouts with the same phone produce ONE customer record with both orders linked
- Customer with `consent.marketingEmail = false` is excluded from any test bulk-email query
- Admin can search `+919876543210` and see the full order + event history for that person
- Daily RFM cron completes in < 30 seconds for 10k customers (benchmarked locally with synthetic data)
- Pincode `400001` lookup returns `{ serviceable: true, codAvailable: true, etaDays: 3 }`

### Depends On

Nothing — purely additive schema changes.

### Threat Model (per Failure-Modes doc)

Must address: 3.5 (duplicate customer), 7.1 (schema rollback safety — all new fields optional), 7.8 (PII leakage — admin role gating from day 1), 6.6 (DPDP deletion path stubbed even if not surfaced in UI).

## Phase 2 — Order Lifecycle Hardening

**Goal:** The order state machine is explicit, enforced, observable, and recoverable. Inventory is held atomically; payment is reconciled; returns/refunds have a real flow. Every state change is logged with `actor` and `reason`.

**Requirements covered:** CRT-01–03, CHK-01–05, PAY-01–07, FUL-01–05, RTN-01–05

### Tasks

1. **Schema additions:**
   - `orderEvents` (with backfill of existing orders to a single `null → {currentStatus}` event)
   - `inventoryHolds`, `inventoryEvents`
   - `paymentLog`, `processedWebhookEvents`, `webhookFailures`
   - `refunds`, `writeOffs`
   - `cartSnapshots`, `productWaitlist`
   - Extend `orders.status` enum to the new state machine; migrate existing values per FUL-03
   - Add `orders.tax`, `orders.trackingId`, `orders.courier`, `orders.parentOrderId`, `orders.addressRaw`
2. **State machine engine** (`convex/orderFlow.ts`):
   - Single `transitionOrder(orderId, toStatus, { actor, reason, metadata })` mutation
   - Static `ALLOWED_TRANSITIONS` table (typed)
   - Throws `INVALID_TRANSITION` with helpful message listing what IS allowed
   - Writes `orderEvents` row in same transaction
3. **Split `submitOrder` into `createDraftOrder` + `finalizeOrder`**:
   - `createDraftOrder` reserves inventory, creates draft with 15-min expiry
   - `finalizeOrder` is called by Razorpay webhook (prepaid) or directly (COD)
   - `expireDrafts` cron releases stale holds and marks drafts `expired`
4. **Razorpay integration:**
   - Convex HTTP action `/razorpay/webhook` with HMAC verification
   - Handle `payment.captured`, `payment.failed`, `refund.created`, `payment.authorized`
   - Idempotent via `processedWebhookEvents`
   - `paymentReconciliation` cron every 15 min
5. **COD flow:**
   - Risk filter computes `riskReasons` array; high risk → `cod-verification` queue
   - Admin queue with OTP-verified confirm button
6. **Returns & refunds:**
   - `requestReturn` mutation (customer-facing; 7-day window enforced)
   - `processReturn` mutation (admin; marks line items resellable/written-off)
   - `issueRefund` mutation; calls Razorpay refund API; writes to `refunds`
   - `retryFailedRefunds` cron (daily, 5 attempts with exponential backoff)
7. **Inventory atomicity:**
   - `availableStock(productId)` helper: `products.stockQty - sum(inventoryHolds.qty where expiresAt > now and orderId.status != released)`
   - Used by `createDraftOrder` AND by the public product page (so out-of-stock is visible in real time)
8. **Server-side total recomputation extends to:**
   - Shipping fee derived from pincode table (not client-supplied)
   - Tax computed via static `taxRate` per state (5% / 12% / 18% buckets seeded for India)
   - Discount re-validation (already exists; preserved)

### Success Criteria

- A customer placing two orders for the last unit simultaneously: one succeeds, one gets `OUT_OF_STOCK` and a clean recovery screen
- Razorpay webhook replayed 10x: order finalizes exactly once
- `payment.captured` webhook lost / delayed: `paymentReconciliation` cron finalizes within 15 min
- Order in `draft` for 16 minutes: inventory hold released, status `expired`, alert NOT sent (this is normal flow)
- Admin transitions `confirmed → delivered`: rejected with "must pass through packed, shipped"
- Order timeline page shows every transition with actor, ts, reason; can be exported as CSV
- Refund retry: failed once, succeeds on attempt 2; `refunds.status` correctly moves `pending → processed`
- COD order > ₹3000 lands in `cod-verification` queue, NOT `confirmed`

### Depends On

Phase 1 (customer linkage for `cartSnapshots`, `customerEvents` for the cart events fired from this phase)

### Threat Model (per Failure-Modes doc)

Must address: every P0 and P1 from the failure modes catalog (4.1–4.10, 3.1–3.4, 5.1–5.10). Each must have a regression test:
- Idempotent webhook test (replay same event 10x)
- Inventory race test (two concurrent `createDraftOrder` for last unit)
- Reconciliation cron test (simulate lost webhook → cron picks up)
- Invalid transition test (each disallowed transition rejected)
- Refund retry test (simulate Razorpay 500, ensure retry)

## Phase 3 — Comms & Observability

**Goal:** Customers know what's happening with their order. Ops can spot anomalies on a dashboard. Abandoned carts come back. Marketing has the data they need without ad-hoc SQL.

**Requirements covered:** NOT-01–04, ABN-01–03, OPS-01–04 + all derived metrics from DATA-CAPTURE.md §9

### Tasks

1. **Schema additions:**
   - `notificationOutbox`, `cronLocks`, `clientErrors`
   - Extend `customerEvents` with the notification-delivery sub-events (no new table needed — just new `type` values)
2. **Notification infrastructure:**
   - Provider adapters: `whatsapp` (Gupshup or Meta Cloud API), `sms` (TextLocal or AWS SNS), `email` (Resend or AWS SES)
   - Template engine: read from `siteContent.crm.templates.{templateKey}.{channel}`, render with strict `{{var}}` substitution, no nested expressions
   - Outbox drainer cron (every 30 sec): pulls up to 50 queued notifications, sends, updates status
   - Provider webhooks (one per provider) update `notification_delivered` / `notification_failed` events
3. **Channel fallback chain:**
   - On `notification_failed` for WhatsApp: re-queue same payload for SMS (if consent), else email
   - After 3 channel failures, write `notification_undeliverable` to `customerEvents` and surface to ops
4. **Abandoned cart pipeline:**
   - `detectAbandonedCarts` hourly cron: identifies eligible carts (CRM-known customer, snapshot > 1hr old, no order in window, no recent abandoned-cart notification within 24h)
   - Templates: `cart.abandoned.t1`, `t24`, `t72` (escalating with optional discount at t72)
   - Deeplink token: signed JWT (`CART_RECOVERY_SECRET` env var, 7-day TTL)
   - `/cart?recover={token}` route validates, restores cart, emits `cart_recovered`
5. **Action Required dashboard:**
   - New section in existing Admin Orders tab
   - Real-time counters via Convex reactivity for: `cod-verification`, `payment-failed`, `delivery-failed`, `return-requested`, pending refunds, stale shipped (>7 days)
   - Click counter → filtered list view
6. **Order timeline UI:**
   - Inline collapsible timeline in admin order row (reads `orderEvents`)
   - Public customer-facing tracking page (`/orders/[id]/track`) — PII-stripped, shows happy-path milestones only (no internal cancellation reasons, no admin notes)
7. **Client error capture:**
   - React `ErrorBoundary` at app root → `logClientError`
   - `window.addEventListener('error' | 'unhandledrejection')` global handler
   - Sampling: 100% on `/checkout`, `/cart`, `/orders/*`; 10% elsewhere
8. **Metrics queries:**
   - Implement all 13 derived metrics from DATA-CAPTURE.md §9 as Convex queries
   - "Analytics" tab in admin (existing `admins.permissions.analytics`) renders them with date-range filter
9. **Provider rate-limiting & retry:**
   - Each provider call wrapped in a token-bucket limiter (e.g., 80 WhatsApp/min for Gupshup tier)
   - 429 from provider → backoff, requeue with `delayUntil`

### Success Criteria

- Customer places an order: receives WhatsApp confirmation within 60 seconds (or SMS fallback if WhatsApp consent absent)
- Customer abandons checkout at the address step (phone already entered): receives t1 email within 90 minutes
- Customer clicks recovery link 5 days later: cart restored exactly as left, `cart_recovered` event emitted
- Ops sees "3 orders need COD verification" badge update in real time as new orders arrive
- A test exception thrown in production `<Checkout>` shows up in `clientErrors` within 60 seconds
- Analytics tab loads with 14 of the 13 metrics displayed (extra: AOV trend chart)
- Provider rate-limit hit: queue continues draining at provider's limit, no errors surfaced to customer

### Depends On

Phase 1 (customer + events) AND Phase 2 (order events).

### Threat Model

Must address: 7.4 (notification spam — unique constraint on outbox), 7.6 (bot rate-limit), 7.7 (webhook DoS — signature-first), 7.14 (third-party outage — feature flags), 2.6 (early phone capture for recovery).

## Cross-Phase Dependencies & Risk

```
Phase 1 (Data Foundation) ──► Phase 2 (Lifecycle) ──► Phase 3 (Comms)
        │                              │
        │                              └──► provides orderEvents read API to Phase 3
        │
        └──► provides customers + customerEvents to BOTH downstream phases
```

**Highest-risk integration:** Phase 2's Razorpay webhook. Recommend a dedicated spike (`/gsd-spike razorpay-webhook-idempotency`) before Phase 2 plan-phase to validate signature verification in a Convex HTTP action with realistic replay scenarios.

**Schema migration ordering** is strict (see DATA-CAPTURE.md §11) — adding all of Phase 1's tables in a single deploy is fine because they're additive and non-breaking. Phase 2's `orders.status` enum extension MUST be deployed before any code reads new statuses, and existing-row migration MUST run before any code requires `packed` to exist.
