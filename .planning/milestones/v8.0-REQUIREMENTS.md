# Requirements: v8.0 — CRM & Order Fulfillment

**Defined:** 2026-05-25
**Core Value:** Every order from add-to-cart to delivered (or refunded) is observable, recoverable, and tied to a customer record we actually own.

**Carries forward from v2.0–v4.0:**
- Guest-only checkout (no customer login) — customer identity is derived from `(phone, email)` tuple, not auth
- Convex backend only — no new infrastructure
- Razorpay for online payment, COD for cash-on-delivery
- India-only addressing (pincode + state)

**Companion docs (read together):**
- `v8.0-FAILURE-MODES.md` — every problem that can happen at each step and the mitigation
- `v8.0-DATA-CAPTURE.md` — exact events, fields, and where they're written
- `v8.0-ROADMAP.md` — phase breakdown

---

## Scope Overview

Three pillars, each delivered as its own phase:

| Pillar | What it adds | Why |
|--------|--------------|-----|
| **CRM data model** | `customers`, `customerAddresses`, `customerEvents`, `cartSnapshots`, `orderEvents`, `refunds` tables | Today the only customer "record" is denormalized on each order row. No LTV, no segmentation, no recovery. |
| **Order lifecycle** | Reservation → payment → fulfillment → delivery → returns state machine with explicit transitions and idempotency | Today: 5 raw statuses + a single `updateStatus` mutation. No inventory hold, no payment reconciliation, no exception handling. |
| **Observability & comms** | Event stream, customer notifications (email/WhatsApp), abandoned-cart recovery, ops dashboard | Today: zero customer-facing comms, no abandoned-cart detection, no per-order timeline for support. |

## 1. CRM Data Model

### 1.1 Customer Identity

- [ ] **CRM-01** — A `customers` table exists keyed by `customerId` (auto). Fields: `name`, `phone` (E.164, normalized), `email` (lowercased), `firstSeenAt`, `lastSeenAt`, `source` (`"shop" | "kiosk" | "widget" | "editorial"`), `tags` (array), `consent` (object: `marketingEmail`, `marketingSms`, `marketingWhatsapp`, each with `granted: bool, ts: number, source: string`).
- [ ] **CRM-02** — Customers are uniquely identified by `phone` (primary) and `email` (secondary). Index `by_phone` and `by_email`. If a checkout submits a `(phone, email)` pair where one matches an existing record and the other doesn't, the system merges by updating the missing field on the existing row rather than creating a duplicate.
- [ ] **CRM-03** — Existing `orders.customerPhone` / `customerEmail` are backfilled into `customers` via a `migrations.backfillCustomers` mutation. Backfill is idempotent — safe to run twice.
- [ ] **CRM-04** — A new `customerId: v.optional(v.id("customers"))` field is added to `orders`; new orders link to a customer row at `submitOrder` time. The legacy `customer` embedded object is kept on orders for historical immutability (address-at-time-of-order must survive even if the customer later edits their default address).

### 1.2 Addresses

- [ ] **ADR-01** — A `customerAddresses` table holds addresses separate from orders: `customerId`, `label` (`"home" | "office" | "other"`), `line1`, `line2`, `city`, `state`, `pincode`, `landmark`, `lat`/`lng` (optional, populated when v3.0-phase-02 GPS autofill succeeds), `isDefault`, `lastUsedAt`. Index `by_customer`.
- [ ] **ADR-02** — At checkout, if the entered address matches an existing one for that customer (fuzzy: same pincode + first 30 chars of `line1` case-folded), reuse the existing address row instead of inserting a duplicate.
- [ ] **ADR-03** — `pincode` is validated against a `pincodeServiceability` table (`pincode: string, serviceable: bool, codAvailable: bool, etaDays: number, partner: string`). Non-serviceable pincodes block checkout with a clear message; partial serviceability (e.g., prepaid-only) disables COD.
- [ ] **ADR-04** — The address form rejects pincodes that don't match a known Indian state (PIN-to-state lookup table seeded once at deployment).

### 1.3 Customer Events Stream

- [ ] **EVT-01** — A `customerEvents` table stores every customer-level event: `customerId`, `type` (see DATA-CAPTURE.md for the full enum), `ts`, `properties` (JSON string), `sessionId`, `orderId?`. Index `by_customer_ts` for timeline queries.
- [ ] **EVT-02** — Event writes are append-only (no updates, no deletes outside a 90-day retention job). The retention cron deletes only events older than 90 days AND tagged `lifecycle: "low-value"`. High-value events (`order_placed`, `order_delivered`, `refund_issued`, `consent_changed`) are kept indefinitely.
- [ ] **EVT-03** — Events written to `customerEvents` are also mirrored to `customerEventsAnonymous` for sessions that never identify (no phone/email yet) — keyed by `sessionId`. When the customer later identifies, a `linkAnonymousSession` mutation merges the anonymous events into their customer timeline by replacing `sessionId` with `customerId`.

### 1.4 Customer Segments & LTV

- [ ] **SEG-01** — A `customerSegments` materialized view (one row per customer, key `customerId`) is maintained by a Convex internal mutation triggered by every order transition: fields `lifetimeRevenue`, `orderCount`, `firstOrderAt`, `lastOrderAt`, `avgOrderValue`, `daysSinceLastOrder`, `rfmRecency` (1–5), `rfmFrequency` (1–5), `rfmMonetary` (1–5), `segment` (`"new" | "active" | "at-risk" | "lapsed" | "vip"`).
- [ ] **SEG-02** — Segment thresholds are configurable via `siteContent` key `"crm.segmentThresholds"`. A daily cron recomputes RFM quintiles across the customer base (RFM scores are population-relative, not absolute).
- [ ] **SEG-03** — The Admin Dashboard Customers tab (RBAC permission already exists in `admins.permissions.customers`) lists customers with filterable segment chips, search by phone/email/name, and per-customer drawer showing all orders + event timeline + addresses.

## 2. Order Lifecycle (Add-to-Cart → Delivered)

### 2.1 Cart & Pre-Checkout

- [ ] **CRT-01** — Cart state lives in `localStorage` (already shipped) PLUS, when a customer is known (phone provided at any point), a `cartSnapshots` row keyed by `customerId` is upserted. Snapshot is a JSON blob + `updatedAt`. Used for abandoned-cart recovery and cross-device sync.
- [ ] **CRT-02** — Every `addToCart` / `removeFromCart` / `updateQty` action on the client emits an analytics event (see DATA-CAPTURE.md §1). Server snapshot is debounced to once per 5 seconds.
- [ ] **CRT-03** — A `cartValidate` query is called when the cart drawer opens and immediately before `submitOrder`. It returns, per line item: `priceChanged` (boolean + new price), `outOfStock` (boolean), `removed` (product deleted), `lowStock` (boolean + remaining qty if `< 5`). The UI must reconcile differences before allowing checkout to proceed.

### 2.2 Checkout & Reservation

- [ ] **CHK-01** — `submitOrder` is split into a two-step flow:
  1. **`createDraftOrder`** — validates address, recomputes totals, reserves inventory, returns `draftOrderId` + `requiredPaymentAmount`. Order row inserted with `status: "draft"` and `expiresAt: now() + 15 min`.
  2. **`finalizeOrder`** — invoked after payment success (or immediately for COD). Transitions `"draft" → "pending"`, sets `paidAt` (for prepaid), kicks off downstream notifications.
- [ ] **CHK-02** — Inventory reservation is atomic. A new `inventoryHolds` table: `productId`, `qty`, `draftOrderId`, `expiresAt`. `createDraftOrder` decrements available stock via `products.stockQty - sum(active holds)`. A cron expires holds past `expiresAt` and bumps the product back. Same product can have many active holds; the running availability calculation is the source of truth, never a stored "available" number that could drift.
- [ ] **CHK-03** — If between `createDraftOrder` and `finalizeOrder` the inventory falls below the held quantity (race with admin manual decrement), the finalize step fails with `INVENTORY_LOST` and the customer is shown a recovery screen with refund/alternate options.
- [ ] **CHK-04** — Server-side total verification (already exists for subtotal) is extended to also re-verify: shipping (from pincode table, not client), discount (already re-validated), GST/tax line (new — add `tax` field to orders).
- [ ] **CHK-05** — The customer's `consent.marketingEmail` is set to `true` only via an explicit opt-in checkbox at checkout (default unchecked). The order itself doesn't imply marketing consent.

### 2.3 Payment

- [ ] **PAY-01** — Razorpay Standard Checkout flow: `createDraftOrder` returns a `razorpayOrderId` created via the server-side `/orders` API. The frontend opens Razorpay with that ID. The webhook is the source of truth for payment status — frontend success/failure callbacks are advisory only.
- [ ] **PAY-02** — Convex HTTP action at `/razorpay/webhook` verifies the `x-razorpay-signature` header against `RAZORPAY_WEBHOOK_SECRET` (HMAC-SHA256 of raw body). Invalid signatures return 400 and are logged to `webhookFailures`.
- [ ] **PAY-03** — Webhook handler is idempotent: events are deduplicated by `razorpayEventId` stored in a `processedWebhookEvents` table. Replay of the same event is a no-op.
- [ ] **PAY-04** — Supported webhook events: `payment.captured` (→ finalize order), `payment.failed` (→ release inventory hold + mark draft failed), `refund.created` (→ insert refund row, transition order to `"refunded"`), `payment.authorized` (logged but not acted on — we use auto-capture).
- [ ] **PAY-05** — A `paymentReconciliation` cron runs every 15 minutes: lists Razorpay payments from the last hour, cross-references against orders. Any captured payment without a corresponding finalized order is flagged (`paymentOrphan`) and ops is alerted. Any pending order older than 30 minutes with no payment is auto-cancelled with inventory released.
- [ ] **PAY-06** — COD orders skip the Razorpay step entirely. `createDraftOrder` returns `paymentMethod: "cod"` directly to `finalizeOrder`. COD orders enter `status: "pending"` and require manual ops confirmation before `"confirmed"`.
- [ ] **PAY-07** — COD high-risk filter: orders > ₹3000 OR pincode flagged `codHighRisk` OR customer with prior `codRejected` event require ops phone-verification before `"confirmed"` (status `"cod-verification"` with a dedicated admin queue).

### 2.4 Fulfillment State Machine

The order goes through these states. Each transition is explicit, logged to `orderEvents`, and bounded by what's allowed.

```
            ┌──────────────────────────────────────────────────────────┐
            │                                                          │
            ▼                                                          │
  draft ──► pending ──► confirmed ──► packed ──► shipped ──► delivered │
    │         │            │                        │           │     │
    │         │            │                        │           ├─► return-requested ──► returned ──► refunded
    │         │            │                        │           │
    │         │            │                        ├─► delivery-failed ──► (retry → shipped) OR (give-up → returned)
    │         │            │                        │
    │         │            │                        └─► lost-in-transit ──► refunded
    │         │            │
    │         │            └─► cancelled-by-ops (+ refund if prepaid)
    │         │
    │         └─► cancelled-by-customer (window: pending only; refund if prepaid)
    │
    └─► expired (auto, 15 min)  /  payment-failed (terminal)
```

- [ ] **FUL-01** — A `transitionOrder` mutation enforces allowed transitions via a static table (above). Disallowed transitions throw `INVALID_TRANSITION`.
- [ ] **FUL-02** — Every transition writes an `orderEvents` row: `orderId`, `from`, `to`, `actor` (`"customer" | "admin:{userId}" | "system:{cronName}" | "webhook:{eventId}"`), `reason`, `ts`, `metadata` (JSON).
- [ ] **FUL-03** — New statuses replace the v2.0 flat enum. Migration: existing `"pending"` rows stay `"pending"`, `"confirmed"` → `"confirmed"`, `"shipped"` → `"shipped"`, `"delivered"` → `"delivered"`, `"cancelled"` → `"cancelled-by-ops"` (default). The `orderSummary` aggregator is updated to count by category (revenue / pending / cancelled) using the new enum.
- [ ] **FUL-04** — Admin status transitions are gated by RBAC: only roles with `orders: true` can transition. Sensitive transitions (`cancelled-by-ops` after `confirmed`, `refunded`, `lost-in-transit`) additionally require OTP re-verification (the existing CMS OTP flow is reused).
- [ ] **FUL-05** — A `packed` status is added between `confirmed` and `shipped` — captures the moment items physically leave inventory and a tracking ID is assigned. `trackingId` and `courier` fields are required to transition `packed → shipped`.

### 2.5 Returns, Refunds, Cancellations

- [ ] **RTN-01** — A `refunds` table: `orderId`, `amount`, `reason`, `requestedBy`, `requestedAt`, `processedAt`, `razorpayRefundId`, `status` (`"pending" | "processed" | "failed"`).
- [ ] **RTN-02** — Customer-initiated cancellation is allowed only in `"pending"` (pre-confirmed). After `"confirmed"`, customer must request cancellation via `requestCancellation` which creates a support ticket — only ops can transition.
- [ ] **RTN-03** — Refund issuance for prepaid orders calls Razorpay refund API. Webhook `refund.created` confirms. If the refund call fails, the row stays `"pending"` and a daily cron retries up to 5 times with exponential backoff.
- [ ] **RTN-04** — Restock-on-return: when an order moves to `"returned"`, inventory is incremented back ONLY if the admin marks each line item as `"resellable"`. Damaged returns are written off to a `writeOffs` table with photo evidence (Convex Storage).
- [ ] **RTN-05** — Return window is 7 days from delivery (configurable per category in `siteContent.crm.returnWindowDays`). Beyond the window, `requestCancellation` is rejected at the API level.

## 3. Observability & Comms

### 3.1 Notifications

- [ ] **NOT-01** — Customer notifications are sent at these triggers (channel preference: WhatsApp > Email > SMS, honoring consent flags):
  - `order_placed` (immediate confirmation)
  - `payment_failed` (with retry link)
  - `order_confirmed` (after COD verification or prepaid capture)
  - `order_shipped` (with tracking link)
  - `out_for_delivery` (if courier API provides; see NOT-04)
  - `order_delivered` (with feedback request 24 hrs later)
  - `cancellation_confirmed`
  - `refund_processed`
- [ ] **NOT-02** — Notifications are queued via a `notificationOutbox` table: `customerId`, `channel`, `templateKey`, `payload`, `attempts`, `status` (`"queued" | "sent" | "failed"`), `lastError`. A cron drains the queue every 30 seconds.
- [ ] **NOT-03** — Templates live in `siteContent` under `crm.templates.{templateKey}.{channel}` so ops can edit copy without a deploy. Templates support `{{handlebars}}` substitution with a strict whitelist of fields.
- [ ] **NOT-04** — Courier integration (Delhivery + Shiprocket) is feature-flagged. When enabled, a webhook receiver at `/courier/webhook` accepts status updates and writes to `orderEvents` with `actor: "courier:{partner}"`. When disabled, status transitions are admin-driven only.

### 3.2 Abandoned Cart

- [ ] **ABN-01** — A cart is "abandoned" if `cartSnapshots.updatedAt` is older than 1 hour AND the customer has a known `phone` or `email` AND no order was placed in the interval.
- [ ] **ABN-02** — An hourly cron scans for abandoned carts and creates a `notificationOutbox` entry with template `cart.abandoned.t1` (1 hour). Follow-ups at 24h (`t24`) and 72h (`t72`) with optional discount injection.
- [ ] **ABN-03** — Recovery link in the notification deep-links to `/cart?recover={token}`. Token is a signed JWT containing `customerId + cartSnapshotId`, valid for 7 days. Clicking restores cart state and emits an `abandoned_cart_recovered` event.

### 3.3 Admin / Ops Dashboard

- [ ] **OPS-01** — A new "Orders" tab section called "Action Required" surfaces orders in non-happy-path states: `cod-verification`, `payment-failed`, `delivery-failed`, `return-requested`, `refunds.status="pending"`. Counters refresh in real time via Convex reactivity.
- [ ] **OPS-02** — Each order row in the admin queue has an inline timeline (read from `orderEvents`) so support agents can see the full history without leaving the page.
- [ ] **OPS-03** — Bulk actions: select multiple orders → bulk-transition (with confirmation showing per-order allowed transitions; disallowed ones are listed and skipped, not blocked).
- [ ] **OPS-04** — Customer drawer (existing RBAC permission `customers`): full order history, event timeline, total spend, RFM segment, addresses, consent flags, notes. Free-text notes are admin-only and stored in `customerNotes` with author+timestamp.

## Out of Scope (v8.0)

| Feature | Reason |
|---------|--------|
| Customer login / authenticated portal | Guest-only design preserved; identity remains `(phone, email)` |
| Loyalty points / referral program | Schedule for v9.0 once we have stable customer records |
| Multi-warehouse inventory | Single inventory pool sufficient at current volume |
| Subscription / recurring orders | Separate scope, requires recurring payment auth |
| In-app chat support | Use WhatsApp deep-link instead — uses existing channel |
| AI-driven segmentation / churn prediction | RFM is the floor; ML on top is v9.0+ |
| Returns pickup scheduling via courier API | Manual coordination in v8.0; automate in v8.1 |
| Multi-currency / international shipping | India-only |
